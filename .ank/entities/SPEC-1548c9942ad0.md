## Objet
Règles du modèle de données que l'interface v2 (ADR-4f6e) manipule : preset
de chaîne, file de traitement, état par vidéo, file de publication,
surveillance des sources. Tout est fichier (TOML sous `presets/`, JSON sous
`state/` et `workspace/<video_id>/`), écrit atomiquement (tmp + replace),
sans valeur de secours silencieuse (ADR-ad2e) : une entrée invalide est une
erreur nommée, jamais ignorée. Aucun nom réel : `ma_chaine`.

## 1. Chaîne et preset (`presets/<chaine>.toml`, clipper/channel.py)
1.1 Le nom de chaîne est le nom de fichier sans extension : `[a-z0-9_-]{1,40}`,
    unique, jamais renommé par l'interface (supprimer + recréer).
1.2 Le fichier est une surcouche de `config.toml` : `load_config(path,
    base=config.toml)` fusionne les clés plates puis chaque section clé par
    clé (le preset gagne, les sous-tables comme `[llm.usages.x]` sont
    remplacées entières), et valide le résultat comme un config complet
    (section inconnue, clé inconnue, mode invalide : ConfigError).
1.3 `[channel]` est validée par `CONFIG_DEFAULTS` de `clipper/channel.py` :
    - `display_name` (str, défaut = nom de fichier), `source_url` (str, page
      chaîne YouTube ou Twitch, vide autorisé = pas de source),
    - `watch` (bool, défaut false), `watch_interval_s` (int, défaut 1800),
      `watch_min_duration_s` (int, défaut 600 : VOD plus courtes ignorées),
    - `mode` (`review` | `auto`, défaut = mode global) : c'est lui, et non le
      mode global, qui s'applique aux vidéos de la chaîne,
    - `slots` (liste de `{day = "mon".."sun", time = "HH:MM"}` , défaut `[]`),
      `timezone` (str IANA, défaut `"Europe/Paris"`),
    - `tiktok_account` (str, défaut `""`, réservé à l'autopost, jamais lu
      avant),
    - `logo` (chemin PNG relatif au dépôt, défaut `""`).
1.4 Un preset sans table `[channel]` reste un preset valide pour la CLI ; pour
    l'interface, une chaîne est un preset qui a `[channel]`.
1.5 Écriture (interface ou `channel.save`) : le dict complet est sérialisé
    (`tomli_w`), relu par `load_config` avec la même base, et seulement alors
    remplace le fichier ; un ConfigError laisse le fichier intact et remonte.

## 2. File de traitement (`state/queue.json`, clipper/worker.py)
2.1 Liste ordonnée d'entrées `{id, video_id, url, channel | null, action
    ("run" | "render"), force_steps: [étapes], enqueued_at, status ("waiting"
    | "running"), pid | null}`. Une entrée `running` porte en plus
    `pid_created_at` (heure de création du processus enfant : entier opaque
    propre à la plateforme, `FILETIME` de `GetProcessTimes` sous Windows,
    `starttime` de `/proc/<pid>/stat` sous Linux, `null` si la plateforme ne
    la donne pas) et `launched_at` (ISO, UTC) ; ces deux champs sont écrits
    avec le pid au lancement et retirés avec lui. Un processus est « vivant »
    pour la file si le pid existe ET que son heure de création est celle
    enregistrée (`worker.process_alive`) : un pid réattribué après un
    redémarrage du PC n'est pas vivant ; une entrée sans `pid_created_at`
    (écrite avant cette règle) se réduit à l'existence du pid. Une entrée
    créée par le worker pour reprendre une vidéo `queued` (§2.4) porte
    `resume: true`. Une seule entrée `running` à la fois : le worker n'en
    lance jamais une seconde, et une entrée `running` qu'il n'a pas lancée
    (enfant d'un worker précédent) dont le processus vit est **adoptée** :
    surveillée par pid + heure de création jusqu'à sa fin (code de sortie lu
    sur un handle Windows, sinon « inconnu » et c'est `pipeline.json` qui dit
    l'issue), son entrée retirée à sa mort, rien d'autre lancé d'ici là ; si
    plusieurs entrées `running` vivantes coexistent (file écrite avant cette
    règle), la première est adoptée et les autres sont journalisées en erreur
    puis reprises à la mort de leur processus.
2.2 Ordre = `enqueued_at`, sauf « passer en tête » qui réordonne les entrées
    `waiting` en conservant toutes les entrées `running` à leur place (jamais
    une entrée perdue). Doublon (même `video_id` et action déjà `waiting`)
    refusé avec erreur. Retirer une entrée `waiting` qui porte `resume: true`
    veut dire « ne plus reprendre cette vidéo » : si son état est encore
    `queued`, la vidéo est retirée des reprises (`dismissed_at`, réversible
    par « Restaurer »), sinon le worker la remettrait en file au tour
    suivant ; une vidéo qui n'est plus `queued` n'est pas touchée.
2.3 Le worker lance l'entrée de tête : `python -m clipper <action>
    [--config presets/<channel>.toml] [--force-step x ...] [--resume] --
    <url|id>` (les options avant l'argument positionnel, `--` devant lui :
    un identifiant YouTube peut commencer par `-` ; `--resume` seulement pour
    une entrée `resume`), enregistre `pid`, `pid_created_at` et
    `launched_at`, attend la fin, retire l'entrée. Annulation : seul le
    processus dont l'heure de création correspond à `pid_created_at` est
    arrêté (un pid réattribué désigne un processus étranger que Clipper ne
    touche pas) ; l'arrêt porte sur tout l'arbre de processus de l'enfant
    (ffmpeg, yt-dlp, `claude -p` : `taskkill /PID <pid> /T /F` sous Windows,
    `killpg` du groupe ailleurs), après `cancel_grace_s` ; l'entrée est
    retirée, l'étape restée `running` repasse `pending`, `pipeline.json`
    reçoit `status = "failed", reason = "annulée par l'utilisateur"`.
2.4 **Démarrage du worker.** Un seul worker par file : si le battement
    `state/worker.json` désigne un autre processus encore vivant (pid + heure
    de création, même à battement périmé), le worker refuse de démarrer
    (`WorkerError` « un worker tourne déjà (pid N, dernier battement il y a
    S s) : arrête-le avant d'en lancer un autre (« clipper serve » lance
    déjà le sien) » ; `clipper worker` l'écrit sur stderr et sort en code 1) ;
    un battement illisible est journalisé et remplacé par le premier battement
    de ce worker. Puis toute entrée `running` dont le processus est mort
    (worker précédent tombé, ou pid réattribué) repasse `waiting` en tête,
    dans l'ordre, sans pid ni heure de lancement, et sa vidéo encore
    `running` est marquée interrompue ; une entrée `running` dont le
    processus vit est laissée et adoptée au premier tour (§2.1).
    **Reprise des vidéos `queued`** (ADR-ad2e, `retry_at`) : à chaque tour,
    avant de lancer la tête de file, chaque vidéo `queued` dont `retry_at` est
    passé devient une entrée de file `resume` : action `run` sur `source_url`
    si sa première étape non `done` précède la revue, `render` sur `video_id`
    sinon ; `channel` = celui de l'état, dont le preset est validé par
    `[watch] presets_dir` / `[watch] base_config`. L'entrée est lancée par le
    worker comme toute autre, dans un enfant `--resume` : la reprise tourne
    hors du processus du worker (battement, publications, surveillance et
    annulation continuent, ADR-35b7 §1), et `attempts` est conservé
    (`manual=False` : la reprise automatique compte pour `max_attempts` ;
    une relance à la main remet `attempts` à 0). Les entrées déjà en attente
    passent avant ; une vidéo déjà en file (en attente ou en cours) n'est pas
    doublée et reste `queued` jusqu'à ce que l'enfant écrive `running` ;
    `retry_at` illisible, `source_url` absent, chaîne disparue ou preset
    invalide : la raison est écrite dans `reason` de l'état et journalisée une
    fois, la vidéo reste `queued` (jamais de repli sur la config globale).
    Le worker n'appelle plus jamais `pipeline.process_queue` ; cette fonction
    reste celle de la CLI `clipper queue` (reprise dans le processus courant,
    `attempts` conservé), et elle lit elle aussi le preset d'une chaîne dans
    `[watch] presets_dir` sur `[watch] base_config`.
    **Battement** : `state/worker.json` = `{pid, at, pid_created_at}` réécrit
    au plus toutes les `heartbeat_interval_s` ; aucun drapeau `busy` (le
    worker ne reprend rien lui-même). Une vidéo `running` est « interrompue »
    si et seulement si aucune entrée `running` vivante de la file ne la porte.

## 3. État par vidéo (`workspace/<video_id>/pipeline.json`, clipper/pipeline.py)
3.1 Champs ajoutés au contrat existant : `channel` (str | null, chaîne dont le
    preset a servi), `enqueued_at`, `steps.<x>.progress` (null | `{fraction:
    0..1, eta_s: float | null, message: str}`), réécrit au plus toutes les
    2 s par le pipeline, remis à null quand l'étape finit.
3.2 Journal par vidéo : `workspace/<video_id>/events.jsonl`, une ligne
    `{at, level, step | null, message}` par transition d'état et par ligne
    de log INFO+ du pipeline pendant la vidéo ; jamais tronqué par le
    pipeline.
3.3 Relancer une étape : `force_steps` remet cette étape et toutes celles qui
    la suivent à `pending` (cache aval invalidé), les précédentes restent.

## 4. Publication (`state/publish/<chaine>.json`, clipper/publish.py)
4.1 Une entrée par clip : `{video_id, clip_id, series_id | null, part | null,
    status, slot_at | null (ISO, fuseau de la chaîne), decided_at,
    published_at | null, error | null}` ; `status` ∈ `approved`,
    `scheduled`, `published`, `failed`, `rejected`. Une entrée prise en main
    par le worker (« en cours ») porte `in_progress_since`, `in_progress_pid`
    (pid du processus qui la pilote) et `in_progress_pid_created_at` (son
    heure de création, §2.1) ; les trois sont remis à `null` quand elle
    quitte l'état « en cours ».
4.2 Approuver un clip : entrée `approved` puis, si la chaîne a des `slots`,
    attribution immédiate du prochain créneau libre après maintenant →
    `scheduled`. Les parties d'une série prennent des créneaux consécutifs
    dans l'ordre des parties ; refuser une partie passe toute la série en
    `rejected` (règle QA existante). Sans `slots`, le clip reste `approved`
    et le calendrier le montre « sans créneau ».
4.3 Déplacer = changer `slot_at` vers un créneau libre (un clip par créneau
    et par chaîne ; conflit = erreur). Marquer publié à la main = `published`
    + `published_at`. Tant qu'il n'y a pas d'API, aucune entrée ne passe
    `published` sans action humaine.
4.4 Un clip absent de `state/publish/` est « à valider ». Un clip dont le
    sidecar dit `ready = false` ne peut pas être approuvé (erreur nommée).
4.5 Éditions : `description` et `hashtags` sont modifiés en place dans le
    sidecar (SPEC-6a47) avec `edited_at` ; modifier `screen_title` relance
    render puis qa pour ce seul clip (file de traitement, action `render`,
    `force_steps = [render, qa]`, option clip ciblé), le sidecar est réécrit
    par le rendu. Une entrée `scheduled`/`published` n'est pas éditable sans
    repasser `approved`.
4.6 Au démarrage du worker, une entrée restée « en cours » passe en échec
    explicite et réessayable **seulement si son pilote est mort ou inconnu**
    (`in_progress_pid` absent, ou pid + heure de création qui ne désignent
    plus un processus vivant) ; une entrée dont le pilote vit encore (un autre
    worker) n'est pas touchée : son post part ou échoue par lui. Pendant la
    boucle, une exception inattendue levée par le traitement des publications
    dues est journalisée une fois avec son type et son message, jamais
    propagée : le worker continue.

## 5. Surveillance (`state/watch/<chaine>.json`, clipper/watch.py)
5.1 Pour chaque chaîne `watch = true`, toutes les `watch_interval_s`, le
    worker liste les VOD de `source_url` par yt-dlp (extraction plate, sans
    téléchargement) ; les VOD de durée < `watch_min_duration_s` et celles déjà
    dans `seen` sont ignorées.
5.2 Fichier : `{checked_at, seen: [video_id...], pending: [{video_id, url,
    title, duration_s, published_at, found_at}], last_error | null}`.
5.3 Une VOD nouvelle : chaîne en mode `auto` → mise en file (`state/queue.json`,
    action run) et ajoutée à `seen` ; mode `review` → ajoutée à `pending` (« à
    confirmer » sur le tableau de bord) ; confirmer = mise en file, ignorer =
    `seen` seulement.
5.4 Une erreur de listage (réseau, yt-dlp) est écrite dans `last_error`, la
    chaîne reste surveillée, rien n'est inventé. Aucun test n'appelle
    yt-dlp : le listeur est injecté.
